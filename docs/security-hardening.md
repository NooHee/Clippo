# Security hardening

This change fixes the most important findings of a security audit of Clippo. Each section says
what the risk was, how it was fixed, and how the fix is tested.

Clippo is a good target for attackers: it sees everything the user copies, and it holds the macOS
Accessibility permission, which lets it type into other apps. So the goal is simple. Only Clippo's
own code, running in Clippo's own page, should be able to use those powers, and secrets should
never be stored.

## 1. The popup can no longer be navigated to another page

**Risk.** Electron windows navigate when you drop a file or a link onto them, like a browser tab.
The preload script runs again on the new page, so a dropped HTML file or a web page would get
`window.clipstack`, the bridge to the main process: read the whole history, write the clipboard,
paste into the focused app. The Content Security Policy does not help here, because a CSP belongs
to a document, and the new document brings its own.

**Fix** (`src/main/security/webContentsGuard.ts`):

- `will-frame-navigate` is cancelled for every renderer-initiated navigation, in the popup and the
  tooltip. Pages loaded by the main process (`loadURL`) are not affected.
- `setWindowOpenHandler` denies every `window.open`, and `<webview>` tags are refused.
- Every IPC handler now checks two things instead of one: the call comes from the popup window,
  **and** the calling frame's URL is the page Clippo loaded (`isAppUrl`). This is defense in depth:
  even if a future change reintroduced a navigation path, a foreign page would be rejected.
- Web permission requests (camera, microphone, location, ...) are denied for the whole session.
- Development mode now requires `!app.isPackaged`. Before, setting `NODE_ENV=development` on the
  packaged app made it load `http://localhost:5173`, where any local process could serve a page.

**Tests.** `webContentsGuard.test.ts` covers the URL check (bundled page, dev server, dropped
file, remote page, malformed input). The end-to-end test tries `location.href = 'file:///etc/hosts'`
and `window.open` from the real popup and checks both are blocked. With the guard removed, both
checks fail.

## 2. Passwords are no longer recorded

**Risk.** Every copied password, 2FA code and API key went into history, stayed on disk and was
shown in the list.

**Fix.**

- Password managers mark secrets with standard pasteboard types, documented at nspasteboard.org:
  `org.nspasteboard.ConcealedType`, `TransientType`, `AutoGeneratedType`, plus two legacy ones.
  `ClipboardWatcher` checks for them with `clipboard.has()` before anything else and skips the
  content (text or image). It also remembers that content, so it is not recorded later if the
  marker disappears while the secret stays on the clipboard.
- The Ignored apps list now comes pre-filled with common password apps (`PASSWORD_APPS` in
  `src/shared/types.ts`). Users can remove any of them in Settings. Existing users get them added
  once through a one-time migration in `parseSettings`, tracked by the `passwordAppsAdded` flag, so
  an app the user removes stays removed.

The marker check is the real protection. The app list is a backup for apps that do not set the
marker, and it depends on the Automation permission to know the frontmost app.

**Tests.** Unit tests cover each marker, concealed images, the marker disappearing, normal
recording afterwards, and the migration. The end-to-end test checks that Electron reports a
custom pasteboard marker through `clipboard.has()`.

## 3. Electron fuses: other programs can no longer run code as Clippo

**Risk.** An Electron app binary contains a full Node.js runtime. With default settings,
`ELECTRON_RUN_AS_NODE=1 /Applications/Clippo.app/Contents/MacOS/Clippo script.js` runs any script
**as Clippo**. macOS attributes that process to Clippo, so the script inherits the Accessibility
permission (synthetic keystrokes, reading other apps) and Keychain access (the key that decrypts the
history). `NODE_OPTIONS` and `--inspect` open similar doors.

**Fix.** Fuses are on/off switches compiled into the Electron binary. They are set once at build
time and cannot be changed without breaking the code signature. `scripts/mac/sign.js` flips them
with `@electron/fuses` right before signing:

| Fuse | Value | Why |
|---|---|---|
| `RunAsNode` | off | Blocks `ELECTRON_RUN_AS_NODE` |
| `EnableNodeOptionsEnvironmentVariable` | off | Blocks `NODE_OPTIONS` injection |
| `EnableNodeCliInspectArguments` | off | Blocks `--inspect` and attaching a debugger |
| `EnableEmbeddedAsarIntegrityValidation` | on | Checks `app.asar` against the hash in Info.plist |
| `OnlyLoadAppFromAsar` | on | Makes the integrity check impossible to bypass |

electron-builder has its own `electronFuses` option, but it runs after the `afterPack` hook,
which is where Clippo signs. Flipping fuses after signing would invalidate the signature, so the
hook flips them itself first.

**Tested** by flipping the fuses on a copy of the Electron binary: before, `ELECTRON_RUN_AS_NODE=1`
ran a script; after, the binary started as a normal Electron app and ignored the variable.

## 4. Settings and entry sizes have limits

**Risk.** Settings come from a file the user can edit or import, so they are untrusted input.

- An unparseable hotkey made Electron throw at startup, before the clipboard watcher started, so
  the app ran without recording anything.
- `pollIntervalMs` had no maximum. Node runs any delay above 2,147,483,647 ms after **1 ms**, so a
  large value turned polling into a busy loop at 100% CPU.
- `maxHistory` and the size of a single entry had no limit, so one copied log file could make
  every save, search and popup open slow.

**Fix.**

- `registerHotkey` catches the error and falls back to the default shortcut.
- `parseSettings` clamps `maxHistory` to 1 to 5000 and `pollIntervalMs` to 100 to 5000 ms
  (`SETTINGS_LIMITS`). Out-of-range values are clamped rather than reset, since 10,000 most likely
  means "as many as possible".
- Text over 1,000,000 characters (`MAX_TEXT_LENGTH`, roughly a 500 page book) stays on the
  clipboard but is not saved in history. History import applies the same limit.

## 5. Electron 28 to 43

Electron 28 stopped receiving security fixes in 2024, and `npm audit` flagged it. Clippo decodes
untrusted data all day (any image copied from the web is shown as a thumbnail), so Chromium fixes
matter. It now runs on **Electron 43.8**, a supported release with no known advisories.

Why not 45, the newest? Electron 44 replaced the synchronous clipboard API (`readImage`,
`readBuffer`, `availableFormats`) with an asynchronous one modeled on the web Clipboard API.
Clippo's watcher and image fingerprinting are built on the synchronous API, so moving to 44+ is a
rewrite of that part, which deserves its own change and testing on a Mac. Electron 43 will be
supported until Electron 46 ships, which leaves time to do it properly.

electron-builder moved from 25 to 26.18 at the same time, and `npm audit fix` updated the
non-breaking build tool dependencies. The remaining advisories are in Vitest and Vite (test and
dev server only, never shipped) and need major upgrades.

## Not in this change

- **Developer ID signing, notarization and the hardened runtime.** These remove the Gatekeeper
  warning and block library injection, but need an Apple Developer Program membership. The release
  notes now give the correct first launch steps for macOS 15 and later, where right-click Open no
  longer bypasses Gatekeeper.
- **Encrypting images on disk**, and pasting by id instead of letting the renderer send the text
  to paste. Both are in the audit report as medium severity.

## How to verify on a Mac

1. Copy a password from 1Password or Bitwarden: it does not appear in Clippo.
2. Drag any file onto the open popup: nothing happens, and the popup keeps working.
3. On a packaged build, run
   `ELECTRON_RUN_AS_NODE=1 /Applications/Clippo.app/Contents/MacOS/Clippo -e "console.log(1)"`:
   Clippo starts normally instead of printing `1`.
4. Settings, Ignored apps: the password apps are listed and can be removed.
